# Model card: vouch-risk

> **Note**: This model card is a copy of `backend/projects/vouch/MODEL_CARD.md` for documentation
> accessibility. The canonical version is auto-generated by `make train-vouch`.

Generated by `make train-vouch` (vouch/models/train.py). Version: v20261010-210128.

## Scoring Thresholds and Policy Integration

The model outputs feed into the policy engine with these thresholds:

| Threshold | Value | Effect |
|---|---|---|
| High risk | any risk head ≥ 0.70 with legitimacy < 0.60 | HOLD lane with "unresolved high fraud risk" |
| Fast-pay eligible | legitimacy ≥ 0.85, all risk heads < 0.30, amount ≤ $2,500 | Automatic payment under owner's standing rule |
| LIME explanation | top risk head ≥ 0.50 | Explains the top risk; otherwise explains legitimacy |

**Model never denies**: The model only adds friction. A risky score can move a card from STANDARD to HOLD,
but Cedar and the kernel rules are authoritative. The model cannot relax a rule or override a kernel flag.

**Fallback behavior**: When the model is unavailable (inference service down, no trained weights), the
scorer automatically falls back to `heuristic-fallback`, a transparent rule-based scorer with the same
output shape. The scorer name is recorded in every audit record.

## What it is
VouchNet, a small PyTorch model trained from scratch on CPU in 2.8s:
- Entity embeddings (dim 4) for vendor country, category, bank country, and the AP clerk who submitted the invoice.
- Shared 2-layer MLP trunk with four sigmoid heads: `ato_bec`, `insider`, `fake_vendor` risk, plus `legitimacy`.
- Autoencoder over the numeric features, trained on honest invoices only. Its reconstruction error, as a
  percentile of honest training error, is the `anomaly` score.
- Graph signal for rings: features from the vendor-attribute graph (vendors linked by shared bank account,
  tax id, phone, address, or non-public email domain): shared-attribute degrees, connected-component size,
  share of new vendors in the component, and one round of parameter-free message passing (mean identity
  red flags of linked vendors).
- LIME explanations per card: on the dominant risk head, or on the legitimacy head for clean cards.

## Data
Seeded synthetic payables world (vouch/synth.py): vendors, invoices, bank accounts, addresses, phones,
tax ids, payment history. Bad actors: ATO/BEC (bank or contact changed, urgency, lookalike remit email),
insider abuse (duplicates, split invoices under the approval limit, creeping amounts, no PO/delivery),
fake/synthetic vendors (invalid tax ids, VOIP phones, virtual addresses, rings sharing attributes).
Honest-but-unusual vendors (new small vendors, confirmed bank changes, seasonal spikes, shared business-park
addresses) are oversampled 3x in the loss so false positives are measured and penalised.

- Train / validation: world seed 11, split by vendor (train 2413 invoices, validation 599).
- **Held-out test: separate world seed 99 (1233 invoices), unseen vendors and rings.**

## System-level outcomes on the held-out test (kernel checks + model + policy)
| metric | value |
|---|---|
| bad-actor invoices put on HOLD | 94.9% (n=311) |
| **honest invoices put on HOLD (false-positive rate)** | **1.1%** (n=922) |
| honest-but-unusual invoices put on HOLD | 0.8% (n=255) |
| honest invoices routed to the fast-pay lane | 2.6% |

A HOLD is never a denial: every hold has a resolution path (out-of-band confirmation, owner review, appeal).
Honest vendors whose bank change was already confirmed out-of-band are not held. The fast-pay share is low
because the fast-pay limit ($2,500) is below most synthetic invoice amounts.

Reading the numbers: ATO/BEC is near-perfect because a bank-detail change that nobody confirmed is an explicit
kernel signal. The model earns its keep on insider and fake-vendor patterns and, above all, on the
legitimacy head that keeps honest-but-unusual vendors (new, small, seasonal) out of the hold queue.

## Limitations
- **Synthetic data only.** The generator encodes our assumptions about fraud patterns, so these metrics
  measure how well the model learns those patterns, not real-world performance. All training and held-out
  test data is generated by `vouch/synth.py` with explicit seeded typologies.
- **Identity checks are stubs.** Tax id checksum, VOIP lookup, and virtual address detection stand in for
  real TIN matching, carrier lookup, and address-verification APIs.
- **Clerk embedding governance needed.** The clerk embedding can learn "this clerk is risky"; in production
  that needs governance (it is a signal for review, never an automatic action against an employee).
- **Thresholds are fixed.** Risk threshold (≥0.70 with legitimacy <0.60), fast-pay gates (legitimacy ≥0.85,
  risk <0.30), and the LIME explanation threshold (0.50) are set by policy, not tuned per customer.

## Usage

```bash
make train-vouch           # Train and register a new model version (~3 seconds on CPU)
make model-serve           # Start the inference service on :8201
make dev-vouch             # API + inference together (Ctrl-C stops both)
```

The API reports the active scorer on `GET /v1/info` and `GET /health`. LIME factors appear in every
payment card under `evidence` (frontend shape) and `lime` (raw model output).
